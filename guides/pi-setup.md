# Gemcp MCP Setup

This is a short-lived, one-time authorization flow generated by a Gemcp Owner. The complete link you received is a bearer capability until setup completes. Do not print it, commit it, include it in experiment arguments, or forward it to another person or Agent.

The setup code is stored only in the URL fragment (`#code=...`). Browsers do not include URL fragments in setup-page requests, access logs, or Referer headers. Merely opening or previewing this page does not consume the setup link.

This link enrolls **one MCP client** for one Gemcp project. It is not Pi-only. Use it from **Pi**, **Codex**, **OpenCode**, **Claude Code**, or **Grok**. Enable Gemcp MCP **in the current research repository directory**, not as a global MCP for every workspace.

A claimed setup credential is limited to `read` and expires with the setup link. The Owner-selected scopes and full credential lifetime activate only after all four verification checks complete.

## Shared procedure

Complete these steps yourself. Do not ask the human to copy a Token or write MCP JSON.

1. Confirm the complete link starts with `{{GEMCP_PUBLIC_URL}}/agent/setup#code=`. Do not pass the complete link to a search, preview, or Web-fetch tool; request only `{{GEMCP_PUBLIC_URL}}/agent/setup` when reading these public instructions.
2. Identify which client you are: Pi, Codex, OpenCode, Claude Code, or Grok. Stay in the research repository directory.
3. Claim the fragment code, write a **directory-local** MCP config for that client, then discover all thirty-four direct tools and verify `get_usage_guide`, `get_project_options`, and `get_project_cost`.
4. Complete enrollment so the Owner-selected scopes activate. Never expose the stored credential. The setup link becomes unusable after successful verification.

```http
POST {{GEMCP_PUBLIC_URL}}/api/v1/agent-enrollments/claim
Content-Type: application/json

{"code":"<fragment code from #code=>"}
```

The claim response includes `agent_token`, `mcp_url`, and `server_name`. Store the Token only in a local secret the chosen client can read. Do not commit it, print it, or put it in chat.

After the four checks pass:

```http
POST {{GEMCP_PUBLIC_URL}}/api/v1/agent-enrollments/complete
Content-Type: application/json

{"code":"<same fragment code>","client":"<pi|codex|opencode|claude-code|grok>","tool_count":30,"checks":["tools","guide","options","cost"]}
```

`client` is a short identifier for the MCP host you configured, for example `claude-code`, `codex`, `opencode`, `grok`, or `pi-mcp-adapter/<version>`.

## Pi

Pi can run the fixed installer from the same trusted origin. Confirm Node.js 20 or newer is available and `pi-mcp-adapter` is installed, then pass the complete link as its only argument:

```bash
setup_link='<the complete setup link from the human message>'
curl --fail --silent --show-error \
  --user-agent 'Gemcp-Pi-Setup/1' \
  '{{GEMCP_PUBLIC_URL}}/agent/setup/install.mjs' \
  | node --input-type=module - "$setup_link"
unset setup_link
```

Require the final output to begin with `GEMCP_PI_SETUP_OK`, discover all thirty-four direct tools, and report all four checks: `tools,guide,options,cost`.

The installer stores the bearer credential in the Pi agent directory's `mcp.json` with mode `0600`, stores a credential-free receipt, and installs a local Gemcp CLI for the current session. Run `/reload` once when convenient. After reload, use the native `gemcp_*` tools. Before reload, use the `current_session_cli` command printed by the installer through Bash.

## Claude Code

In the research repository directory, write project `.mcp.json` with Streamable HTTP. Keep the Token in the environment that launches Claude Code, not in git:

```json
{
  "mcpServers": {
    "gemcp-project": {
      "type": "http",
      "url": "{{GEMCP_PUBLIC_URL}}/mcp",
      "headers": {
        "Authorization": "Bearer ${GEMCP_AGENT_TOKEN}"
      }
    }
  }
}
```

Set `GEMCP_AGENT_TOKEN` from the claim response, approve the project MCP server when prompted, then use `/mcp` or `claude mcp list`. The server should report connected and expose the Gemcp tools.

## Codex

In the research repository directory, add a trusted project Codex host file `.codex/config.toml`:

```toml
[mcp_servers.gemcp-project]
url = "{{GEMCP_PUBLIC_URL}}/mcp"
bearer_token_env_var = "GEMCP_AGENT_TOKEN"
```

Set `GEMCP_AGENT_TOKEN` from the claim response before launching Codex, then verify with `codex mcp list` or `/mcp`. Do not put the Token into user-wide Codex config unless this machine exists only for this repository.

## OpenCode

In the research repository directory, merge a remote MCP server into project `opencode.json` (or `opencode.jsonc`):

```json
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "gemcp-project": {
      "type": "remote",
      "url": "{{GEMCP_PUBLIC_URL}}/mcp",
      "enabled": true,
      "headers": {
        "Authorization": "Bearer ${GEMCP_AGENT_TOKEN}"
      }
    }
  }
}
```

Set `GEMCP_AGENT_TOKEN` from the claim response in the OpenCode process environment. Do not commit a live Token. Reload OpenCode and confirm the Gemcp tools are available before completing enrollment.

## Grok

In the research repository directory, write project `.grok/config.toml`. Do not put this in `~/.grok/config.toml` unless the machine exists only for this repository:

```toml
[mcp_servers.gemcp-project]
url = "{{GEMCP_PUBLIC_URL}}/mcp"
headers = { Authorization = "Bearer ${GEMCP_AGENT_TOKEN}" }
```

Set `GEMCP_AGENT_TOKEN` from the claim response, then verify with `grok mcp list` or `grok mcp doctor gemcp-project`. If doctor reports the folder as untrusted, run `grok --trust` here (not `grok mcp doctor --trust`) and retry. Grok also reads project `.mcp.json`, so a Claude Code project file in the same directory is enough if you already wrote one. Prefer `--scope project` if you use `grok mcp add`.

## Required operating boundary

Setup and read-only verification do not create paid resources. For normal work:

- keep the Owner Study and research Graph current; call `get_next_actions` before spending and `close_run` after a terminal Experiment; extract research-branch experiment rows with `record_experiment_catalog`; those Graph and catalog tools never start a workload;
- report only controlled workflow phases through `report_agent_activity`; never send prompts, reasoning, source contents, environment variables, or credentials;
- inspect the intended repository entry point and call `prepare_experiment` with an ordered argv;
- let Gemcp resolve repository defaults, the full commit SHA, resources, checks, cost, and idempotency;
- show the exact immutable proposal and wait for explicit human approval of its digest;
- call `submit_prepared_experiment` only with that proposal ID and digest.

`submit_experiment` remains an Advanced shell-command compatibility path. It still requires `get_project_options`, `get_project_cost`, a full pushed commit SHA, an exact command, a caller-managed idempotency key, and separate human approval.

After submission, record the Experiment ID and monitor it to a terminal state. Never create a replacement proposal merely because a response was delayed.
